# Decisions

## No backend

The task is planning with private numbers by one person. A static site removes accounts, a database,
backups of other people's data and most of the attack surface, and it works offline. Cost: no sharing and one
plan per browser; files cover moving and backing up. A future sync service would be an addition, not a
rewrite, because the whole state is one serialisable value with a versioned format.

## Scenarios store changes, not copies

Alternatives: copy the whole plan per scenario, or store diffs computed after the fact. Copies make "change the
rent everywhere" impossible and make "what does this scenario assume?" a diffing problem. Storing explicit
changes keeps both simple: `resolve` is a fold over the lineage, and the change list is the explanation.
Rules that keep it tidy: a value set back to the parent's value removes the override; structural edits prune
changes that point at removed lines. Depth is not limited, the scenario count is (8), which also fixes the
number of identity colours.

## Undo by snapshots

Command objects with inverse operations are more memory-efficient but every edit type needs a correct inverse.
Immutable snapshots with structural sharing make undo trivially correct for every edit, including imports
and deletes of whole scenario trees. 100 steps of a plan of this size are a few hundred KB at most.
Coalescing by field key with a one-second window matches how people type numbers.

## Hand-written chart

A chart library would add 40-100 KB and still need work for keyboard reading, dash patterns and direct
labels. The chart has one job (balances over months, up to four lines), so about 250 lines of SVG code do it
with full control over accessibility. Colours come from a palette validated for colour-vision deficiency
and contrast in both themes (see [DESIGN.md](DESIGN.md#colour)); identity never relies on colour alone.

## Zod for the file format

The import path has to reject anything malformed with messages a person can act on. Zod gives strict objects
(unknown keys rejected), cross-field checks (tree has one baseline, no cycles, unique ids) and issue paths. It
costs 24 KB compressed in the initial bundle because autosaved data is validated at start-up. `zod/mini`
would save some of that at the price of a more verbose schema; left as an exercise.

## React Router

Four views with real URLs (`/compare` can be bookmarked and printed). The router is 14 KB compressed and is
also what the service worker's app-shell fallback expects. A hand-written router was considered and rejected
as not worth the risk for the size.

## Service worker without a library

Workbox would be the usual choice. The needs here are small (precache everything, cache first, explicit
update), so a 40-line worker generated by a 30-line Vite plugin keeps the behaviour readable and testable.
Explicit update instead of `skipWaiting` on install: the person decides when the page reloads.

## localStorage, not IndexedDB

A plan is tens of kilobytes. `localStorage` is synchronous, simple and available everywhere; writes are
debounced. IndexedDB would matter for many plans or large attachments, which are out of scope.

## Format versioning

Every file has `format: "planwright"` and an integer `version`. Older versions are upgraded step by step
(`MIGRATIONS[n]` turns n into n+1); newer versions are refused with "reload to update". Format 2 added
`cadence`; a real format-1 export is kept as a test fixture so the migration is tested against an actual old
file, not a hand-written one.

## nginx-unprivileged for serving

Static files need no application server. nginx gives precompressed files, cache headers and security headers
in configuration, runs as uid 101, starts in milliseconds and idles at about 2 MiB. Read-only filesystem
with a small tmpfs.
